# Куток — конвенції вайрфреймів

> Правила для всіх наступних вайрфреймів. Оновлено після рішення перейти
> до повного набору мобільних web-прототипів. Джерела: `sitemap.md` (перелік
> екранів, сутності, поля) і `wireframes/_screens.md` (job, місце у flow і
> реальні стани шести екранів головного flow). Цей документ фіксує **як**
> малювати; фактичне покриття 15 екранів × 4 стани перевірене в `_critique.md`.

---

## 1. Рівень деталізації: структура, не оформлення

Вайрфрейм показує ієрархію й зони — не те, як продукт виглядатиме.

- Лише відтінки сірого: білий фон, сірі поверхні/бордери, чорний або
  темно-сірий текст. Жодного кольору — і це стосується й станів: сторінка
  помилки чи успіху не отримує червоного чи зеленого «для наочності» (те
  кольорове кодування, яким `flows.md` розфарбовує вузли діаграми, —
  прийом самої діаграми, не інструкція для вайрфрейму). Стан читається з
  тексту й розмітки, не з кольору.
- Без шрифтових рішень — системний шрифт браузера за замовчуванням, без
  підбору гарнітур, розмірів-акцентів, ваги.
- Без бренду — ні назви-логотипу як графічного елементу, ні тону голосу
  з CLAUDE.md («тепло, по-домашньому») у візуальному оформленні. Текст
  може бути реальним (правило 3), але без брендової стилізації.
- Без реальних картинок — жодних фото чи ілюстрацій. Якщо зона під фото
  структурно потрібна (наприклад, фото оголошення чи профілю — обидва
  поля позначені `[?]` в `sitemap.md`, без прямого job), вона з'являється
  тільки якщо конкретний екран цього вимагає, і показується як порожній
  підписаний блок («Фото»). Для профілю використовується круглий плейсхолдер
  аватара, для житла — прямокутний плейсхолдер фото.
- Системні chrome-позначки в `_wireframe.css` можуть бути геометричними
  SVG-масками, але не задають продуктову іконографіку. Готовий продуктовий
  набір зʼявляється лише на двох кольорових екранах уроку 6.
- Радіуси дозволені як частина прототипу мобільних патернів: 12 px для
  контролів, 16 px для карток, кругла форма для аватарів і чипів.
- Сірі поверхні мають сталі ролі: зовнішнє полотно, корпус пристрою,
  основний контент, піднята картка/поле, вкладена зона, active/pressed.
  Темний графіт зарезервований для головної CTA та активного індикатора.

## 2. Розмітка: семантичний HTML

Структура сторінки виражається тегами, не суцільними `<div>`.

Мінімальний набір і коли який використовувати:

| Тег | Коли |
|---|---|
| `<header>` | Шапка екрана: заголовок, кнопка «назад», глобальна нав-панель |
| `<nav>` | Глобальна навігація (Пошук / Чати / Оголошення / Профіль) і будь-який список посилань-переходів |
| `<main>` | Єдиний контентний блок екрана поза header/nav/footer |
| `<section>` | Смислово окрема зона всередині `<main>` (напр. «Фільтри», «Звички», «Відповідь на заявку») |
| `<article>` | Самодостатня одиниця контенту, що повторюється у списку — картка оголошення в стрічці, картка профілю, рядок чату в списку заявок |
| `<form>` + `<fieldset>` + `<label>` | Будь-який ввід даних — форма заявки, форма оголошення, форма фільтрів |
| `<button>` | Дія (надіслати, застосувати, поскаржитись) |
| `<a>` | Перехід між екранами (усередині `<nav>` або як посилання з картки) |
| `<ul>`/`<li>` | Список однорідних елементів (стрічка карток, список чатів, список звичок) |
| `<table>` | Тільки для справді табличних даних — у списку екранів такого поки немає |
| `<dialog>` | Контекстні bottom sheet / модальні екрани (напр. «Налаштувати фільтри») |

`<div>`/`<span>` — лише як обгортка для розмітки/розкладки (grid/flex),
коли жоден семантичний тег не підходить, і ніколи як заміна `<section>`
чи `<article>`.

## 3. Текст: зі словника продукту, не lorem ipsum

Увесь текст на вайрфреймі — реальні дані з домену Кутка, взяті з
`sitemap.md` (поля сутностей) і брифу `CLAUDE.md` (персони, райони,
бюджети):

- Оголошення: район/метро Києва, ціна в межах 5–11 тис. грн (діапазон
  Марічки з `research/personas.md`), умови (меблювання, тварини),
  побажання до співмешканця (охайність, гості, куріння, режим дня).
- Профіль: імʼя, «про себе», бюджет і райони інтересу, ті самі звички,
  статус верифікації телефону, бейдж «перевірено».
- Заявка/чат: реальний текст першого повідомлення («Привіт! Кімната ще
  вільна? Можна дізнатись більше про сусідів?»), а не «Message text
  here».
- Фільтри: ті самі поля, що й у профілі/оголошенні (район, бюджет,
  звички) — конкретні значення, не «Filter option 1/2/3».

Мета — щоб вайрфрейм одразу перевіряв, чи вміщується реальний контент
(довгі райони, тризначні бюджети, довгі побажання), а не ховав це за
абстрактним заповнювачем.

## 4. Назви файлів

```
wireframes/<назва>.html            — базова сторінка (нормальний вигляд екрана)
wireframes/<назва>-empty.html      — порожній стан
wireframes/<назва>-error.html      — помилка
wireframes/<назва>-loading.html    — завантаження
```

- `<назва>` — латинська kebab-case назва екрана (напр. `listings` для
  «Стрічка кімнат», `listing` для «Картка оголошення кімнати»). Назва
  фіксується один раз, у момент, коли екран реально малюється; фактичні
  файли перелічені й перевірені в `_critique.md`.
- Базовий файл без суфікса — це **нормальний робочий вигляд екрана**
  (дані завантажені, форма готова, картка показує реальне оголошення).
  Це не те саме, що позначка «Успіх» у `_screens.md`/`flows.md` (вона
  означає конкретний кінцевий вузол flow, наприклад «T» у Flow 1). Так,
  «Картка оголошення кімнати» в `_screens.md` не має власного вузла
  «Успіх» (flow завершується успіхом пізніше, на екрані чату) — але
  базовий файл `listing.html` усе одно існує: це її звичайний вигляд.
- Суфіксні файли (`-empty`, `-error`, `-loading`) утворюють повну матрицю
  прототипних станів кожного екрана. Якщо flow не називає стан окремим
  вузлом, сторінка все одно показує реальну поведінку мобільного web:
  перший вхід/порожню форму, збій мережі або валідації, skeleton чи процес
  надсилання. Анотація чесно відрізняє сценарний вузол від системного стану.

## 5. Стани: окрема сторінка на кожен, та сама структура

Кожен реальний стан — самостійний HTML-файл, не JS-перемикач всередині
одного файлу і не коментар «// показати, якщо порожньо» в розмітці.

- Структура (набір семантичних тегів, ієрархія секцій) в усіх станах
  однієї «назви» екрана — та сама. Різниться лише вміст: де в базовому
  файлі стрічка карток (`<ul><li><article>…`), у `-empty` — та сама
  `<section>`, але замість списку — повідомлення «Нічого не знайшлось»
  і, де це передбачено flow (`_screens.md`), дія (наприклад, посилання
  на розширення фільтрів).
- `-error` показує повідомлення про помилку в тому самому місці, де в
  базовому файлі був би результат дії (наприклад, на екрані картки
  оголошення — там, де в нормальному вигляді була б кнопка «Надіслати
  заявку», у `-error` до неї додається текст «Заявку не надіслано,
  спробуйте ще раз»).
- `-loading` показує текстову позначку стану («Надсилаємо заявку…») на
  місці елемента дії, без спінерів чи анімації (це вже оформлення,
  правило 6).
- Приклад із зафіксованих у `_screens.md` станів: «Стрічка кімнат» →
  `listings.html` (успіх/список) + `listings-empty.html`. «Картка
  оголошення» → `listing.html` (базовий вигляд) + суфіксні стани. Повна
  матриця чотирьох сторінок реалізована для всіх екранів за контрактом
  уроку 4, навіть якщо ранній `_screens.md` вимагав менше.

## 6. Мобільні web-патерни

- рамка 393 px, а на вузькому viewport — повна ширина та `100dvh`;
- системний status bar зверху й home indicator знизу входять у рамку
  пристрою; продуктова bottom navigation розміщена над home indicator;
- окремий scroll контенту між верхньою панеллю і bottom navigation;
- основні touch-зони не менше 44×44 px, поля та рядки вибору — 48 px;
- заголовок app bar завжди геометрично по центру; перехід назад — окрема
  44×44 іконка-chevron зліва без текстової кнопки;
- кнопки в контентній зоні займають повну ширину; компактними лишаються
  лише системні кнопки app bar, tab bar та надсилання в composer;
- відступи будуються на шкалі 4/8/12/16/24/32 px;
- перемикач типу стрічки — суцільний 44 px segmented control із рівними
  сегментами та окремою піднятою поверхнею активного сегмента;
- глобальна навігація знизу, contextual back у верхній панелі;
- фільтри та підтвердження — bottom sheet; довгі форми мають доступну
  основну дію біля нижнього краю;
- зі стрічки фільтри відкриваються круглою 56×56 FAB над bottom navigation;
  самі фільтри завжди показані як sheet, що піднімається знизу й має
  власний scroll;
- skeleton повторює структуру майбутнього контенту; помилка зберігає введені
  дані та дає повторити дію; порожній стан пояснює наступний крок.

## 7. Що лишаємо на потім

Свідомо не в цьому кроці:

- Колір (палітра бренду, семантичні кольори станів).
- Шрифт (гарнітура, розміри, накреслення).
- Тіні та фінальна глибина (elevation).
- Готові продуктові іконки поза двома екранами уроку 6.
- Готовий, відполірований UI — анімації, мікровзаємодії, реальні фото.
