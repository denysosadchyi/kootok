# Правила роботи агентів — Куток

Спільний контракт для Claude Code і Codex. Це єдине канонічне місце для
правил роботи з репозиторієм; `CLAUDE.md` імпортує цей файл, тому правила
тут не дублюються більше ніде.

**Перед будь-якою роботою прочитайте `CLAUDE.md`** — там продуктовий бриф
(проблема, персона, IA, ключові рішення, відкриті питання) і поточний
дизайн-контракт. Codex не завантажує `CLAUDE.md` автоматично, тому це явна
вимога, а не побажання.

## Що є каноном, а що ні

- Канон дизайн-системи: `design-system/index.css` (єдина точка входу),
  `design-system/tokens.css` (два рівні: primitive → semantic),
  `design-system/components/` (модулі; declarations читають значення через
  `var()`), `design-system/patterns/` (повторювані композиції; правила й
  поріг «щонайменше 3 сторінки або 3 екземпляри з однаковою семантикою» —
  `design-system/patterns/README.md`),
  `design-system/docs/` (жива документація компонентів). Продуктова мова й
  правила застосування — `DESIGN.md`; обґрунтування атрибутів — `concept.md`.
- Активний прототип — рівно 4 макети в `beginners/source/prototype/`
  (публічний alias `lesson-6/`): `listings`, `listing`, `compatibility-form`,
  `application`; п'ятий екран сценарію — «Чати» (`design-system/examples/chats.html`,
  зібраний лише з кіта) — показується в тій самій курсовій рамці. Правила саме
  цього шару — `beginners/source/prototype/_rules.md`.
  Решта ранніх макетів — в `archive/early-prototype/`, продуктові wireframes —
  в `archive/product-wireframes/`; архів не є активними сторінками й не
  підключається в навігацію.
- `ui/kit.html`, `ui/tokens.html`, `ui/shell.html` — оглядові/навчальні
  артефакти, не канон документації. `beginners/source/` поза `prototype/` —
  архівний знімок ранніх уроків; його `CLAUDE.md`, `PRODUCT.md`, `README.md`
  та `product/` не є чинними правилами.
- Єдина веб-точка входу до артефактів — `index.html`. Курсова панель
  (`course-nav.*`) і desktop frame навколо екрана не є частиною продукту.
- Backlog і статус вимог — `IMPLEMENTATION_PLAN.md`; прогалини кіта —
  `design-system/backlog.md`. У `CLAUDE.md` і `DESIGN.md` статусну хроніку
  не вносити.

## Внесок у систему

Правило одне: будь-яке нове спочатку з'являється в `design-system/`, потім на
екрані — ніколи навпаки. Не робіть локальний screen-only варіант із обіцянкою
винести його в систему згодом.

- **Новий компонент або його варіант** — модуль у `design-system/components/`,
  створена або оновлена сторінка в `design-system/docs/` з усіма релевантними
  станами у світлій і темній (`[data-theme="dark"]`) темах. Лише після цього —
  застосування на екранах.
- **Нова композиція чинних компонентів** — файл у `design-system/patterns/`,
  потім екрани. Не дублюйте композицію як локальний виняток екрана.
- **Нове або змінене значення** — `design-system/tokens.css` на правильному
  рівні: raw value — primitive, продуктова роль — semantic (посилається на
  primitive). Компоненти й екрани не споживають literal. Колір, типографічні
  ролі, spacing- і radius-ролі — лише semantic; primitive напряму допустимі в
  `components/` тільки для геометрії (length/width), іконок, тривалості й
  font-weight. Екрани primitive не споживають. Кожен новий semantic token
  визначається в обох темах (якщо значення в темній темі відрізняється).

**Правило «залишаємо».** Якщо користувач каже «залишаємо», правка стає
частиною системи: value change → token правильного primitive/semantic рівня;
component change → `design-system/components/` і відповідна сторінка
`design-system/docs/` зі станами в обох темах; new composition →
`design-system/patterns/`. Після системного внесення застосуйте рішення на всіх
релевантних екранах. У новій сесії виконуйте це з коду, не перепитуючи.

## Робочий процес

- Кореневий агент фіксує нову користувацьку правку в `IMPLEMENTATION_PLAN.md`
  як backlog item з owner і одразу делегує її; для простих правок план не є
  блокуючим ритуалом.
- Усі файлові правки виконує призначений агент. Кореневий агент не редагує
  реалізацію: координує, делегує, перевіряє результат.
- Призначений агент об'єднує пов'язані дрібні правки в один batch і запускає
  один консолідований QA наприкінці batch, а не після кожної micro-change.
- Після делегування кореневий агент чекає статус, перевіряє один batch QA і
  лише після успішної перевірки переводить вимогу в `done` та дає висновок.
- Накопичені вимоги не замінюються новою правкою: кожен активний пункт
  лишається в плані до окремого підтвердження виконання.
- Перевірка після batch: `scripts/audit-local-links.mjs` і
  `scripts/qa-lesson-8.mjs` (import graph, активні маршрути, assets,
  responsive layout, доступність, відсутність legacy-посилань). Сервер — з
  батьківської теки (`cd /home/hp/from-den && python3 -m http.server <port>`),
  origin передається аргументом без `/kootok`, CDP-порт — `KOOTOOK_CDP_PORT`;
  докладніше — README «Як запускати QA». Не додавати в
  продукт runtime CDN-шрифти чи data URI для іконок — шрифти self-hosted в
  `assets/fonts/`, іконки в `tokens/icons/`.
- Анімацій у продукті й курсових сторінках немає: жодних transition,
  animation, keyframes чи плавного скролу; токенів тривалості немає. Стани
  змінюються миттєво.
- Мова документації, інтерфейсу й коментарів — українська; технічні терміни
  та назви продуктів — в оригіналі.
